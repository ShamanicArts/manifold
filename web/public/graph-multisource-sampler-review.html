The authored graph

Live input 1 → Fixed gain ×4 7 → Retrospective capture 6. Sidechain input 8 → Fixed gain ×4 9 → Retrospective capture 10. Both capture nodes are silent processing roots with their own 30-second rings. MIDI input 4 → Sample instrument 5 → Output 3 is the audible path.

The old source IDs 0 and 1 map to capture nodes 6 and 10 in this particular graph. The graph stores the chosen node ID, timing mode, bar length, and browser tempo; these are checked when loading a project. Rust/Wasm converts bars to an exact frame count before staging a snapshot. A sounding note retains its earlier PCM; later notes use the new source.

Verified: the direct Wasm worklet probe measured independent gain-scaled rings (input 0.25 → 1.0; sidechain −0.75 → −3.0), silent output before notes, held-note continuity, and exactly 6,000 frames for 1/16 bar at 120 BPM. Chromium captured 165 Hz and 330 Hz test sources separately and retained source 10 plus a 0.1-bar, 120-BPM window through download and reopen. Native project preparation and the Rust workspace suite pass.

Browser → plug-in proof

A saved Chromium sidechain take is kept as a portable project fixture. The VST3 component and CLAP plug-in entry point load that exact bundle, receive a MIDI note, and produce the same 128 audio frames as the native Rust reference. Their state saves retain source node 10, the 0.1-bar window at 120 BPM, and 9,600 frames of embedded PCM. This proves browser capture can be reopened and played through either plug-in adapter.

Next contracts

The browser tempo is a manual setting. Recording and publishing a new source from inside a DAW, reading its actual transport timing, and free-capture offsets still need host controls. Dynamic source registration, old numeric-ID import, the complete eight-subvoice instrument, phase vocoder modes, and legacy analysis are also open. Publication is user-triggered. These synthetic worklet, Chromium, and adapter checks do not measure physical audio-device underruns or establish full C++/Lua parity.
