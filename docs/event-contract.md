# Timed note event contract

The voice foundation introduces `TimedEvent { offset, node, kind }` in Rust. `offset` is a zero-based frame position **inside the next block**. Events are ordered by offset, with insertion order preserved for events at the same frame. The graph validates all offsets and destinations before processing, renders each span up to an event, applies the event to its target node, then renders the remaining span. This makes an event at frame 127 distinct from one at frame 128 across 128-frame blocks.

The event kinds are note on, note off, all notes off, and pitch bend. A zero-velocity note on acts as note off. The voice node has eight fixed slots, retriggers the same channel and note, uses a free slot when available, and otherwise steals the oldest active slot. Note off enters release from any envelope stage. This fixes the old `MidiVoiceNode` scalar path's attack-stage note-off behavior as an intentional redesign; these voice cases are compared with native Rust, not presented as C++ parity.

The [Standalone Transpose slice](midi-transpose-migration.md), [Main rack Note Filter](midi-note-filter-migration.md), and [Main rack Scale Quantizer](midi-scale-quantizer-migration.md) transform MIDI events inside the typed Rust graph. Their `MidiInput → effect → VoiceSynth` paths use fixed eight-slot note ownership and remap held notes when relevant parameters change. The worklet delivers an incoming event to `MidiInput` when it becomes due, so future events are not treated as held notes early. The graph forwards transformed events at the same frame offset. Velocity mapping, arpeggiation, and MIDI output ports remain to be built.

MIDI transform nodes keep a fixed 32-entry trace of emitted and suppressed note events with node ID, channel, note, velocity, and within-block offset. A parameter change that remaps held notes records its off/on events at offset zero. The browser requests this trace at 10 Hz from the worklet message handler and displays only new sequence numbers. The audio callback stores entries in the prepared ring; it sends no UI messages. The trace is diagnostic and may overwrite old entries if more than 32 arrive between polls.

The authored `SampleRegion` node also accepts note-on as a retrigger and all-notes-off as a stop. It does not yet map note pitch to playback speed, assign multiple voices, or honor note-off gates. Its browser view has a trigger button. The separate `SampleInstrument` node accepts the same typed note events for eight independent voices and uses the browser keyboard and optional Web MIDI adapter.

The Wasm ABI reserves 256 events in each prepared engine. `manifold_event_push` appends to the queue without allocating; `manifold_process` consumes and clears it. Browser keyboard events enter at offset zero of the next available block. Hardware MIDI messages carry their Web MIDI `Event.timeStamp` into the audio host. The host maps that performance clock to AudioContext time using `getOutputTimestamp()` when available, adds 12 ms of lookahead, and enforces at least two 128-frame render quanta of lead. It falls back to `currentTime` plus the event's age when the output timestamp is unavailable. The AudioWorklet keeps a separate, preallocated 256-event queue ordered by absolute frame; it pushes due events to the Rust queue at their within-block offsets. Late arrivals clamp to offset zero. A target's all-notes-off clears its pending events so old note-ons cannot sound after a stop. This provides sample-offset scheduling for timely browser MIDI delivery; device and browser jitter, clock calibration, and host output latency still need measurement on hardware.

Offline fixtures supply arbitrary offsets to verify the Rust timing contract. The on-screen keyboard uses zero-based channel 15 (MIDI channel 16); optional Web MIDI input preserves each device message's channel, note, and velocity. The **Request MIDI access** button calls `navigator.requestMIDIAccess({ sysex: false })` after user interaction, handles device hotplug, and reports denied or unavailable access. The in-app browser may block permission. The instrument views keep six recent note, pedal, and bend events with source, channel, note, and velocity; hardware messages received while audio is stopped are labeled *received only*. The event list is a main-thread diagnostic and does not drive DSP. No Lua is imported. Web MIDI defines the input [event timestamp](https://www.w3.org/TR/webmidi/); Web Audio defines the [output timestamp pair](https://www.w3.org/TR/webaudio/).

The voice node is a playable baseline with sine, saw, square, triangle, ADSR, level, and stereo centre output. Its oscillator and envelope are integrated into one voice kernel for now. A separate standard-waveform Oscillator is now patchable in the graph. The typed `MidiInput` source is present; additive oscillator modes, further modulation nodes, and the fuller authored MIDI Synth project and its effects remain to be ported or redesigned.

The separate patchable `ADSREnvelope` currently uses a gate parameter, independent of note events. The browser gate button sends that parameter to the next worklet block. Its early-release behavior deliberately differs from the old C++ scalar node, which may wait until sustain after a gate-off during attack or decay.

The browser MIDI adapter handles note on, note off, zero-velocity note on, sustain pedal CC64, and 14-bit pitch bend. The wheel uses the old `MidiVoiceNode` range of one octave up or down, centered at 8192, but v2 applies it per MIDI channel to active and future notes. The sample instrument bends its playback cursors on the same channel. The on-screen bend slider sends channel 16 events without requiring hardware MIDI permission. `manifold_event_push` kind 3 packs the raw wheel position into its existing note (LSB) and velocity (MSB) bytes; the worklet schedules it at the message's frame offset. Multiple MIDI devices on one channel use the latest bend message.

Note ownership is tracked by source, channel, and pitch; pedal state merges across devices on the same MIDI channel. A pedal on one input can hold a keyboard on another. The final pedal-up releases only pitches no longer physically held, and reattacking a sustained pitch retriggers it. The on-screen keyboard participates in the same ownership map on channel 16, so a hardware input on that channel cannot accidentally release its note. Disconnecting a device or stopping MIDI input releases its physical and sustained notes without cutting off the same pitch held elsewhere. Disconnecting the last pedal source releases other devices' sustained notes on that channel. Other controllers, including aftertouch, are not mapped yet. See the [Web MIDI API specification](https://www.w3.org/TR/webmidi/) for the browser permission and input event contract.
