# Multitap delay migration boundary

The original `dsp/core/nodes/MultitapDelayNode.cpp` uses one prepared stereo ring buffer and up to eight taps. Rust graph kind 41 follows its scalar signal behavior without JUCE. Parameter 0 selects 1–8 taps, 1 sets feedback (`0…0.95`), and 2 sets internal wet mix (`0…1`). For tap `n` from 1 to 8, parameters `3 + 3(n−1)` through `5 + 3(n−1)` set time (`1…3000 ms`), gain (`0…1`), and pan (`−1…1`). The [workbench](../projects/multitap/project.json) shows the first two tap groups and the common controls; all eight groups are available through the graph API and used in the C++ captures.

The node reads both delay channels at each tap's fractional position, sums them to mono, and distributes that tap with square-root pan gains. Its stereo wet sum feeds back into the matching delay channel. Feedback and internal mix smooth per sample over 10 ms. When mix and feedback are both effectively zero, the original node resets its ring and copies dry input; the Rust port keeps that dormant bypass rule. The prepared Rust ring uses generation stamps, so selection changes and dormant transitions invalidate old samples in constant time without clearing its roughly 1.5 MB audio buffer on the callback.

Standalone FX type 9 maps normalized `p/0` to rounded tap count `2…8` and `p/1` to feedback `0…0.95`. The old Lua definition assigns time, gain, and pan for taps 1–4 and leaves taps 5–8 at the C++ node defaults. It holds internal mix at 1 and applies 1.4× wet gain before the public slot mix. The other three normalized controls are unused.

Seven checked-in C++ captures cover default taps, tap count, feedback, pan/gain, fractional time changes, mix smoothing, and dormant bypass. All compare **Match** against Rust/Wasm with zero observed sample difference on this machine. Four new slot cases compare native Rust with Rust/Wasm for normalized controls and switches. These establish node output parity and v2 slot consistency; old project routing and preset roundtrips remain separate work.
