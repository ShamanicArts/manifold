# When the Manifold core can be called ported

Audit: 28 September 2026. This is an acceptance gate for **transposing legacy projects**, not a count of DSP functions already written. The original Main implementation at `/home/shamanic/dev/my-plugin/UserScripts/projects/Main` is the behavior reference. Keep that checkout read-only.

## Current verdict

**The Manifold core is not yet ported in the project-authoring sense.** Native/Wasm DSP primitives, a typed graph, a substantial assembled Main instrument, browser audio, and Linux CLAP/VST3 hosts work. The Main browser screen now places six prepared modules from a saved rack document. Rack and Patch are two faces of those same shells, with working prepared audio cables, live drag reflow, and a compact Filter width toggle. The separate “Routes” control still scrolls to legacy modulation selectors. Arbitrary module insertion, deletion, sizes, and general typed graph publication remain open.

The legacy Patch view is **the same rack layout with each active shell's performance face replaced by a generated port panel**, plus rail terminals and a wire overlay. It is not a separate unconstrained canvas. `Main/lib/ui/patchbay_generator.lua:713` switches the faces; `Main/ui/behaviors/rack_wire_layer.lua` draws wires and implements port drag and snap. `Main/ui/components/rack_module_shell.lua` provides a delete button, movable header, and width toggle. Its accent strip is explicitly a temporary debug visual, so pixel fidelity should follow the actual widgets and measured references rather than copying that strip blindly.

## Evidence and gaps

| Contract | Working evidence | Missing for the core gate |
| --- | --- | --- |
| Signal kernels | `manifold-core` builds native and Wasm; Main's looper, voice bank, filter, FX and many control stages have signal probes. | Make the Main route graph authorable and compileable from module/edge state; finish parity on supported edge behavior. |
| Graph model | `GraphDescription` validates typed Audio/CV/MIDI connections for graph projects. | A canonical versioned project model shared by Main and other projects: stable module instance IDs, types, parameters, resources, layout, named typed ports, and explicit edges. Main's `rackSnapshot()` currently serializes fixed fields; `MainInstrument` uses a fixed internal order and bounded selector routes. |
| Live mutation | Some prepared routes and up to four LFO slots change while playing. | Add, remove, reorder, resize and connect arbitrary supported instances through a control-side graph compiler. Publish replacement plans at audio block boundaries and migrate eligible node state. No compile, allocation, lock or filesystem work on the audio callback. |
| Rack and Patch UI | Several original faces and compact controls are visible and interactive. | Reuse shell controls, matching dimensions/skin, palette insertion, drag placement, constrained row layout, delete/expand, generated patch faces, port hit targets, rail terminals, wire preview/snap/removal and connection feedback. Both views must project one state. Main audio shell positions now follow the saved grid document; most utility modules still use fixed baseline positions that shift when the audio rack gains rows. |
| Portable state | Browser/native sessions carry many fixed Main controls and captured PCM. Graph projects can cross browser and Linux hosts. | Save and reopen the full module list, position/size, every edge and resource; stable automation IDs and migrations for older sessions. Browser and native host must render and edit the same project contract. |
| Reference projects | Standalone FX, Standalone Sample and Main behavior slices run on the new engine. | Port multiple unlike legacy projects by describing modules/edges/widgets without another one-off Main-style instrument or page. Compare original UI actions, signals, state and host behavior. |

## Specific acceptance sequence

1. **Specify the canonical project document.** Define module instance IDs separately from module types, port IDs and directions, Audio/CV/MIDI/bus compatibility, connection multiplicity, cycle policy, parameter and resource ownership, layout grid and schema version. Build an importer from the current Main fixed session format. The UI and Rust compiler consume the same document.
2. **Compile an editable Main slice.** Start with Source → Filter → FX → output plus one CV route, with graph edges derived from the document. Add Main looper and voice stages as prepared graph nodes or explicit composite modules. A cable edit must change audible output; disconnect restores the correct base path. Prepare and swap plans off the callback while preserving held notes, tails and loops where the node identity is unchanged.
3. **Port the rack shell and real Patch mode.** Match the original 236 × 220 grid and module faces. Implement the left delete control, center drag handle and right width toggle as real actions. In Patch mode, replace performance faces with typed port panels in the same shells and draw cables between port locations. Palette add, remaining face sizes, remove, wider patch/unpatch, and page scroll must update one document and the audible graph. Filter width already persists; drag reorders the six prepared audio faces. Do not call a selector strip a patch view.
4. **Close the state and host loop.** Save a modified rack and connections in the browser, reopen it, load it in CLAP and VST3, automate stable controls, save in the host, and reopen with the same layout, cables, resources and sound. Reject invalid cables with an explanation without mutating the audible plan.
5. **Prove transposition, not only one demonstration.** Port at least three unlike existing projects through the same module/port/widget interfaces: the Main MidiSynth rack, a sample instrument, and an FX or control graph. The latter two should require project descriptors and reusable module adapters, not custom engine branches or copied rack pages. For each, keep an original reference scenario with interaction, rendered signal and state roundtrip. Missing specialized kernels may still need ordinary node implementations; the authoring, routing, layout and host systems should not need redesign.
6. **Run the safety gate.** Verify large and varying block sizes, timed MIDI and automation, multiple instances, live edits, resource limits and clean failure. Measure callback allocation/lock behavior and audio discontinuity around plan swaps. Compare native and Wasm outputs with stated numeric tolerances. Physical-device and DAW validation must complement muted headless browser tests.

Passing these gates supports “the core can carry other Manifold projects.” It does **not** mean every historical media service, special DSP algorithm, preset, platform build or exact pixel has already been ported. The scope of remaining per-project work should be module behavior and authored presentation, rather than a new runtime architecture.

## Immediate next implementation slice

Extend the current Main rack document beyond its six fixed audio modules. The next authored slice should put a real control module and its typed CV connection into the same rack, then let browser and native hosts prepare that module set from the document. After that, port another compact face and the remaining shell actions against the shared document. Keep Main available as the behavior baseline, and treat the existing route selector strip as a separate transitional control surface.
