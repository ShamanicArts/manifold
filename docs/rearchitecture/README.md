## Objective and correction

Latest native authoring evidence: [native JS Sample](native-js-sample-authoring.md)
uses the same Rack/Instrument project entries in QuickJS and the browser, with
timed event admission, bounded target batches, live PCM and fresh-controller
restore. Its next gate is CLAP/VST3 script event/batch handoff and release DAW
evidence; the complete port and Main sequence remain active.

Manifold exposes DSP primitives through a **language-neutral project graph contract**. Project logic builds a graph, finds nodes and endpoints, changes connections and parameters, reacts to control events, and continues when its editor is closed. Authors can write that logic in Rust or JavaScript; TypeScript compiles to the JavaScript binding. These are authoring choices over the same project model and observable graph behavior, rather than separate engines. Rust owns DSP kernels, graph validation and compilation, timed audio events, and real-time state. Project code orchestrates these primitives outside the audio callback. Lua is a behavior reference, not a required v2 language.

Presentation is a separate client of that model. Following Lucas's 1 October
clarification, users choose immediate or retained presentation, and internal
products choose per interaction. Rust [egui](https://github.com/emilk/egui)
supports native and browser/Wasm immediate views; JS/TS can drive a bounded
immediate widget/painting binding or retained web controls. The shared UI kit
owns common control semantics, themes and project bindings with distinct renderer
implementations. Custom Rust egui and arbitrary web framework/HTML/Three.js views
use the same project API. Browser surfaces require explicit focus, positioning,
accessibility and state integration; native web views require a webview adapter.
See the [UI choice in the vertical plan](vertical-delivery-plan.md#ui-choice-shared-kit-immediate-and-retained-presentation).
A UI renderer never owns project logic or audio timing. Existing DOM/Three.js
behavior remains part of migration coverage until ported or explicitly redesigned.

Rust project code normally needs a build step: package native and Wasm artifacts ahead of loading, or run an explicitly supported development-time compiler and hot-reload pipeline outside the audio process. A web browser does not compile ordinary Rust source on project load. JS can be loaded by a control runtime; TS requires transpilation. This distinction must be reflected in packaging, reload, error reporting, and distribution. [Rust target documentation](https://doc.rust-lang.org/rustc/platform-support/wasm32-unknown-unknown.html) and [Cargo build documentation](https://doc.rust-lang.org/cargo/commands/cargo-build.html) describe compilation to Wasm and compiled artifacts; [egui's integration guide](https://github.com/emilk/egui) describes its frame and rendering requirements.

Preserve each legacy behavior or improve it with measured evidence. An unimplemented behavior remains an open task. Retiring or changing a behavior for product reasons requires an explicit user decision and a migration story; implementation convenience is not a completion criterion.

The original `UserScripts/projects/Main/dsp/main.lua` constructs the looper and synth graph using `ctx.primitives` and `ctx.graph`. `Main/dsp/midisynth_integration.lua` changes live connections; `Main/ui/behaviors/rack_mutation_runtime.lua` adds and removes modules. `DSPPluginScriptHost`, `PrimitiveGraph`, and the binding contract harness expose graph, parameter, path, and endpoint behavior. These are product capabilities to transpose, with deliberate improvements recorded explicitly. The old runtime's shared node ownership and mutation pauses are implementation defects to improve, not contracts to preserve.

V2 currently has valuable Rust kernels, `GraphDescription`/`ExecutionPlan`, browser and native adapters, widgets, fixtures, and DAW proofs. It also has a bespoke `MainInstrument` with a fixed voice/capture/monitor/looper order and a constrained rack insert. The Graph editor edits topology only while stopped, and the native project reader loads JSON rather than running a project script. The existing `MainInstrument` and its UI are **behavior oracles and migration sources**, not the completed Main architecture. The default post-voice route now has one DSP owner; a different prepared insert still briefly duplicates graph storage during startup replacement. See the [recovery ledger](main-recovery-ledger.md) for measurements and remaining gates.

Current code entry points: `crates/manifold-core/src/graph.rs` owns the reusable compiler and plan; `crates/manifold-core/src/main_instrument.rs` holds the bespoke Main assembly; `web/src/graph/topology.js` and `web/src/graph/editor.js` edit a graph document; `web/src/state/rack-document.js` and `web/src/state/main-rack-graph.js` handle the constrained Main rack; `crates/manifold-native/src/project.rs` loads native graph JSON. Adapt these boundaries in place before creating another product-specific engine.

## How the previous goal diverged

The thread first measured progress by kernel signal parity, workbench views, and packaged host proofs. These are necessary evidence, but none required an old project script to build and operate a new graph. Main then became a fixed Rust assembly to reach audible looper and voice behavior quickly. When the missing Patch/Rack behavior was identified, the recovery work added a saved shell document and restricted graph insert around that assembly. It did not close the missing script host, project API, or general live mutation. The 28-project inventory and the acceptance contract below prevent a future run from mistaking a working primitive, a visual shell, or a single bespoke instrument for the old Manifold authoring system.

## Non-negotiable acceptance contract

1. A project package contains a versioned manifest, an implementation of project logic in Rust or JavaScript (including transpiled TypeScript), a separate optional presentation entry point, resources, and saved state. A documented packaging path builds Rust for native and browser/Wasm targets. Project behavior runs without a UI or DOM and while a native plug-in editor is closed.
2. Rust and JS/TS bindings implement one documented graph contract to create and query instances; connect typed Audio, CV, gate, voice, and MIDI ports; declare parameters and endpoints; set values or timed events; handle control events; and request graph transactions. Equivalent operations produce equivalent snapshots, errors, timing semantics, and persisted identity in browser and native hosts. Neither binding gives project code direct callback-thread access.
3. Rust validates and prepares graph changes away from every audio callback: AudioWorklet, standalone native, VST3, and CLAP. An accepted transaction becomes audible at a block boundary; a rejected transaction leaves the graph, sound, and saved project unchanged. Resource preparation and old-plan retirement stay off the callback. Surviving instance IDs retain eligible voices, loops, captures, and effect tails under explicit continuity rules.
4. One versioned project state identifies script/package version, module instances, ports, graph edges, parameters, resources, UI layout, host bindings, and continuity state as appropriate. Save/reopen works in browser, standalone native audio, CLAP, and VST3. Import of existing v2 Main sessions and chosen legacy projects is specified and tested; unsupported old state fails with a useful reason.
5. Rack and Patch are projections of the same project graph, with egui as the preferred immediate-mode renderer on native and browser/Wasm. Palette add, delete, move, resize, patch, and unpatch change that graph through the public contract and survive recall. JS/TS presentation bindings can issue equivalent model edits and frame/widget/painting commands where required. HTML elements may be integrated for browser-specific needs through a defined overlay/portal bridge. No visual cable may imply an unsupported DSP route; transient egui frame state is distinct from persisted project layout.
6. At least three unlike original projects—Main, a sample instrument, and an FX or control project—run through this one graph contract without a project-specific host processor or copied graph controller. At least one representative graph project is authored through each Rust and JS/TS binding and compared across browser, standalone native audio, CLAP, and VST3. The old project's graph behavior, audio/MIDI, control response, layout intent, and state are compared case by case. Intentional improvements are documented with old and new outcomes.
7. The audio path stays bounded and real-time safe. Performance is measured against both the original C++ graph and v2 native/Wasm under matched workloads, plus actual browser AudioWorklet, standalone native audio, VST3, and CLAP callbacks. Audio tests use a verified private virtual/null sink.

## Decisions that require explicit design records

- Which project module ABI, artifact format, and loading strategy let compiled Rust project logic run in both native and browser hosts while preserving graph identity and host isolation; prototype before committing.
- Which native JavaScript engine and module format meet project lifecycle, packaging, security, and control-thread cost requirements; prototype before committing. Define how TS builds into that JS format.
- Whether development-time Rust source compilation/hot reload is worth shipping, and how build errors, compiler/toolchain availability, latency, and artifact validation work. Do not assume a DAW plug-in or browser contains a Rust compiler.
- Whether native plug-in editors should embed egui directly or load egui/Wasm in the current webview; measure lifecycle, input/focus, resizing, rendering cost, and distribution in a real DAW.
- Which JS/TS UI calls map to egui widgets or painting, and which browser capabilities require coordinated HTML elements; define frame lifetime, stable widget IDs, coordinate mapping, focus, accessibility, and persisted layout before promising unrestricted UI parity.
- Which old presets/projects import automatically, which need conversion, and which behavior changes are intentional. R00 supplies the evidence; do not infer compatibility from v2 session numbers.
- Whether a composite Rust node is the right reusable boundary for voice allocation, a loop layer, and sample capture. The criterion is that scripts still own graph composition and identity.
- How stable host automation IDs and discoverable parameter paths coexist with dynamic graph instances and DAW fixed-parameter rules.
- Which media and ML services are host capabilities outside the DSP callback, and what projects do when a host lacks one.
- What hardware and block/voice/project workloads define the performance gate. Current parity cases and Node/Wasm timings are useful baselines, not an old C++ versus web result.

Record each decision with alternatives, consequences, old behavior, v2 behavior, and tests. The user's project intent and corrections take precedence over earlier phase-1 architecture prose.
