# Standalone FX routing boundary

The old `fx_slot.lua` connects input to a dry Gain and to each lazily created effect. Each effect output passes through its own Gain gate into a wet Mixer; the wet Mixer passes through a trim Gain into an output Mixer, alongside the dry Gain. Selecting another effect closes the old gate and opens the new one. The created effect node stays connected to input, so its internal state can continue advancing with its gate closed. All Gains use the C++ `GainNode` 10 ms one-pole smoothing. The two Mixers use centered equal-power pan for each bus, giving a factor of about `0.7071068` per Mixer stage at pan zero.

With identity effect outputs and unity Mixer bus/master gains, the internal slot output for a constant stereo input is:

`output = input × 0.7071068 × dry_gain + sum(effect_output × gate_gain) × wet_trim × 0.5`

The [C++ probe](../tools/legacy-fx-routing-probe.cpp) runs the original scalar Gain and Mixer nodes in that layout. The [Rust routing module](../crates/manifold-core/src/fx_routing.rs) reproduces the gain and gate envelopes, while the [probe script](../scripts/probe-fx-routing.py) compares an 8,192-frame stereo capture and draws the [result](../artifacts/reviews/checkpoint-72-routing.png). Native Rust and C++ matched exactly in this identity-effect case. A 1.4× wet trim settles at output/input `0.700`; a 1.1× wet trim settles at `0.550`. The initial dry path settles at `0.707`. The old project may have gain outside the FX slot; this measurement is explicitly at the slot boundary.

The v2 `EffectSlot` selected-only mode keeps its cheaper processing rule: it resets a selected kernel, blends its output with unity dry input, and does not advance unselected kernels. The optional persistent mode now joins the prepared kernels with `LegacyFxRouting`, while keeping the existing mode and fixtures unchanged. A full-project comparison still needs the actual graph-runtime and plug-in path and the old lazy first-selection behavior. The browser exposes persistent routing as a separate project with its own version 2 control-state JSON. The existing version 1 selected-only JSON remains unchanged. Neither format saves internal DSP tail memory; a host format that needs it will require a separate design.

A second [real-kernel switch probe](../tools/legacy-fx-tail-reference.cpp) combines the original C++ Chorus and StereoDelay with those scalar Gains and Mixers. Delay starts selected at fully wet mix, Chorus is first processed when selected at frame 8,192, and Delay remains processing with its gate closed until it is reselected at frame 16,384. The Rust [paired renderer](../crates/manifold-core/examples/render_fx_tail.rs) uses the ported kernels and `LegacyFxRouting`. Across 32,768 stereo frames, the maximum C++ ↔ native Rust difference is `4.47e-8`. A separate diagnostic pauses and resets Delay while it is hidden; after reselecting Delay, that changes output by as much as `0.184`. An impulse sent to the hidden Delay at frame 9,500 still appears in the persistent route after it is selected again. See the [plot](../artifacts/reviews/checkpoint-73-tail.png), [metrics](../artifacts/reviews/checkpoint-73-tail-metrics.json), and [audition files](../artifacts/reviews/checkpoint-73-persistent.wav).

This is an isolated two-effect fixture. Both kernels and gates are prepared at the start; Chorus begins processing at first selection. The old Lua wrapper creates new effects lazily, so its first-selection preparation and gate startup require a separate graph-runtime capture. The fixture does not prove the complete project input/output scaffolding or CPU cost.

The prepared Rust `EffectSlot` now also has an opt-in persistent routing mode. It allocates stereo scratch for all 21 kernels at preparation, marks types as visited on selection, processes only visited kernels each callback, and passes their outputs through `LegacyFxRouting`. Returning to a type does not reset its kernel. The selected-only mode keeps its original behavior and fixtures. Wasm graph kind `52` exposes the persistent mode separately from kind `19`; both share the seven public type/mix/normalized parameter IDs. The [Wasm switch run](../artifacts/reviews/checkpoint-74-wasm-metrics.json) agrees with the old isolated C++ Chorus/Delay capture to a maximum `4.32e-7` over 32,768 stereo frames. A new Rust test visits all 21 types. The [Standalone FX tails browser view](../web/public/reference/standalone-fx-routing/manifest.json) runs kind `52` live and offers the isolated C++ Delay → Chorus → Delay comparison, with a returning-tail plot. Running every visited kernel indefinitely is an explicit CPU cost; a bounded tail policy would change old behavior and needs separate design and measurement.

The [callback timing checkpoint](../artifacts/reviews/checkpoint-76.md) measures that cost on this machine with 128-frame blocks at 48 kHz. Three batches of 512 callbacks each give a median-of-batches of 173 µs for Wasm after all 21 effects have been visited, versus 4.1 µs for the selected-only Delay. This is about 6.5% of the 2,667 µs block duration for the DSP call alone. The Node/Wasm and native CLI runs omit AudioWorklet scheduling, browser graph overhead, host plug-in overhead, and other system load; their maxima include scheduler interruptions. Keep persistent routing opt-in until an in-browser callback and whole-project budget is measured. A time-limited tail policy would be a separate behavior, not an invisible optimization of this mode.

## Old host boundary after a type change

The [first-selection source audit](../artifacts/reviews/checkpoint-78.md) narrows the comparison claim. The original Lua `ensureInstance` creates and connects an unvisited effect and gate, then `applySelection` sets the gate target to one. FX type parameters are marked `deferGraphMutation = true`; the host compiles a new `GraphRuntime` after the deferred callback. Runtime preparation calls `prepare` on **every compiled node**, and the C++ `GainNode::prepare` sets its current gain to its target. Thus a newly selected gate may start fully open on the new runtime rather than follow the 10 ms fade in the isolated fixture. `StereoDelayNode` offers explicit continuity transfer, but `ChorusNode` does not; matching delay state also depends on the runtime's continuity identity/index check. These are source-derived possibilities, not a measured plug-in output. The isolated C++ and Wasm capture tests old node arithmetic and prepared persistent routing; a real host-path capture is needed before calling it full old plug-in behavior.

The [old graph-runtime swap probe](../artifacts/reviews/checkpoint-79.md) now measures part of that path with the original C++ `PrimitiveGraph`, `GraphRuntime`, `GainNode`, and `StereoDelayNode`. Recompiling after setting a closed gate target to one yields first-sample gain `1.0`; changing the target without a recompile yields `0.002081`. A delay tail survived both a same-topology swap and a topology change that inserted a Gain before the same delay object. Explicit continuity transfer counted one for the same-topology swap and zero for the changed-topology swap, but the same node instance retained its buffer. This probe does not invoke Lua or build the full FX slot graph, so the next capture still needs the actual branch selection sequence.

The [branch graph capture](../artifacts/reviews/checkpoint-80.md) now constructs that sequence from the Lua slot layout using the old C++ graph runtime and scalar nodes. Chorus exists at startup, Delay is added on its first visit, and every type change recompiles the runtime. It matches the prepared route before the first switch, then differs by up to `0.0670` during Chorus and `0.0761` after returning to Delay. At the first switch frame the graph output is `0` versus `0.0631` in the prepared route; at the return frame it is `-0.02956` versus approximately `0`. The prepared mode is therefore an intentionally distinct routing experiment, not host-switch parity. The C++ reconstruction still bypasses Lua binding and the deferred worker, and uses scalar Mixer/Gain implementations; actual plug-in output remains to capture.
