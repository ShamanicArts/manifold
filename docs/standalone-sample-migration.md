# Standalone Sample migration boundary

The old `Standalone_Sample/dsp/main.lua` is a sample instrument, not a single loop node. It builds an eight-voice note router and a dynamic sample slot, accepts live or sidechain capture, maps note/pitch/gate controls, and delegates file loading, sample regions, analysis, and playback to several C++ nodes. `SampleRegionPlaybackNode` also owns unison, detune, spread, reverse, crossfade, peak and partial analysis, asynchronous worker jobs, and file decoding. `RetrospectiveCaptureNode` has its own bounded history and peak cache. A direct port needs separate control, audio, and background-task contracts.

The current [Loop capture project](../projects/loop-capture/project.json) is an authored v2 **time and sampling study**. It captures a bounded stereo window from browser audio input, replays it with speed and reverse controls, and can overdub. It uses no file service or Lua. The input remains audible during recording and is dry when playback is stopped. Record starts a new take; stopping record leaves the loop paused until Play is turned on. Recording longer than capacity retains the newest frames. Overdub adds scaled input to the current loop sample and clamps to ±1. Control messages take effect at worklet block boundaries; the kernel allocates only when prepared.

The [Sample region project](../projects/sample-region/project.json) now adds file-backed stereo playback as a separate authored v2 slice. The browser decodes audio at 48 kHz before playback and accepts files up to 30 seconds and 32 MB. The worklet reserves and receives interleaved stereo storage before reporting ready. The Rust node reads that storage with linear interpolation at the source/output rate ratio, selected play and loop points, speed, reverse, one-shot, equal-power seam crossfade, and timed note retriggering. Browser file changes require stopping and restarting the instrument; this avoids storage allocation in the audio callback. Seven native Rust/Wasm cases cover looping, one-shot, reverse, region/speed, retriggering, and crossfade in both directions. The loop-capture and sample-region projects remain separate, and neither imports Lua.

The sample view draws 256 stereo peak bins and play/loop markers. A separate Rust/Wasm worker now computes the bins, peak, RMS, and a bounded pitch estimate from built-in, file, or captured PCM; it returns only a compact summary. An explicit **Use detected root** button maps a reliable estimate to the instrument's MIDI root. The pitch method is a v2 study rather than a port of the legacy `PitchDetector`/`PartialsExtractor`; transient or unreliable signals receive no root suggestion. A two-float meter reports Sample region playhead and playing state at 10 Hz, independent of audio rendering. File input is disabled while the instrument runs so the waveform cannot show a pending source while the graph plays the previous one.

The [Sample instrument project](../projects/sample-instrument/project.json) now adds an eight-voice note router over one shared decoded sample. Each note has one to four prepared subvoice playheads with classic resampling speed, up to 32 cursors total; note on/off, velocity, channel, root note, key tracking, and oldest-voice stealing stay in Rust's timed event path. Browser keyboard and permitted Web MIDI devices feed the same path. An authored 0–200 ms note release lets a voice finish without a hard audio cut; zero retains an immediate stop, while All Notes Off stays an immediate panic stop. Released tails count as active until silent and are recycled before held voices. Unison count takes effect on new notes; detune and stereo spread can change held notes. Nine bounded meter values report the active note count and one playhead per note, polled at 10 Hz. Ten native Rust/Wasm cases cover note overlap, pitch, velocity, channels, stealing, one-shot, key tracking, release, and three unison scenarios. The browser exposes the file, keyboard, and MIDI controls before the longer parameter stack.

A stopped [Loop capture](../projects/loop-capture/project.json) take can now be sent to Sample instrument, [Granulator](../projects/granulator/project.json), Main voice bank, or Main sample blend as its source. Rust copies the ring oldest-to-newest in chunks through prepared Wasm scratch, and the browser holds the transferred stereo PCM while it switches projects. Both Main destinations analyze the captured source in a worker and save it as embedded PCM in their project bundle; the bank resets old targets before a new one is auditioned. The [browser review](../web/public/main-capture-transfer-review.html) covers this path. The editable graph adds a [live sampler study](../projects/graph-workspace/live-sampler.json): a LoopCapture node records the graph's external stereo input. Its current ring window can be published to the running SampleInstrument without stopping recording, or a stopped take can be published as before. Held notes continue on their previous source; new notes use the latest publication. The [recording-window review](../web/public/graph-recording-window-review.html) describes the new path. A [sidechain sampler graph](../projects/graph-workspace/sidechain-sampler.json) provides a distinct second stereo bus for the capture path; the browser can feed it from an independent test oscillator or a microphone. The current Loop Capture view has a two-second capacity. Publication happens only when the user requests it; automatic source replacement each block remains open. A separate [retrospective sampler study](../projects/graph-workspace/retrospective-sampler.json) now records continuously into a 30-second ring without a Record switch. Its capture branch is a silent graph root, and the user selects a recent 0.05–30-second window. The [review](../web/public/graph-retrospective-sampler-review.html) includes early zero padding, native project loading, Wasm audio and Chromium save/reopen.

The old C++ source blends its tail region near `loopEnd` regardless of playback direction. The v2 slice blends near the active seam in both directions, skips the overlapping head on wrap, and leaves one-shot playback unfaded. This symmetric reverse behavior is an intentional redesign; the seven comparisons use native Rust references and do not claim exact C++ parity.

The [two-source retrospective graph](../projects/graph-workspace/retrospective-multisource.json) now represents the old live input and sidechain source entries with independent continuously recording rings. Each has the old fixed input gain of four before capture. The browser selects either source by stable capture node ID, publishes a 0.05–30-second recent window to the instrument, and saves the selected source and window in the graph bundle. The [two-source review](../web/public/graph-multisource-sampler-review.html) includes a direct Wasm worklet proof of separate rings, gain, silence before notes, and held-note continuity, plus Chromium capture and save/reopen. Original numeric source IDs 0 and 1 correspond to authored graph nodes 6 and 10; this is a bounded project mapping, not a general legacy importer.

The old `sample_synth.lua` timing decision is isolated in [Rust capture timing](../crates/manifold-core/src/capture_timing.rs). It prefers host `samplesPerBar`, falls back to a four-beat bar at the host tempo, rounds retrospective bars to a frame count, and measures a free-mode span across one ring wrap. The original Lua three-case free-capture test and the corresponding Rust cases pass. The browser graph now offers bars at a manual tempo or seconds; the AudioWorklet calls the Rust/Wasm helper to convert bars to frames before staging. Its 30-second ring rejects a longer bar request. The browser test proves 0.1 bar at 120 BPM yields 9,600 frames at 48 kHz and survives save/reopen. Actual DAW transport timing, free-mode arming, and write-offset reporting remain pending.

A real [browser-exported sidechain take](../artifacts/fixtures/two-source-browser-capture.json) crosses into both native plug-in adapters. The VST3 component and CLAP plug-in entry point load the same portable bundle, play its 9,600 embedded PCM frames on a MIDI note, match the native graph's first audio block exactly, and preserve the source choice and capture window in state saves.

The [native capture control path](../web/public/native-sampler-capture-review.html) freezes either running ring, copies its PCM outside processing, and prepares a portable replacement project with the selected capture ID. The [new mailbox proof](../web/public/native-capture-mailbox-review.html) runs this transfer during active processing in both VST3 and CLAP callbacks. The callback only touches prepared buffers and bounded lock-free queues; the host control path encodes portable state and prepares the next runtime. Adapter tests drive 75 sidechain blocks, capture 9,600 frames, check the ×4 PCM and MIDI playback, and preserve the take in a state save. Both graph editors offer source and seconds-window capture. CLAP uses its host main-thread action queue; VST3 uses controller-to-processor messages and returns the updated portable state to its controller. The editor gestures still need live DAW testing. Publishing a full replacement currently restarts both capture rings; later state transfer must retain their histories. DAW bars and transport synchronization remain future work.

The v2 projects still do not reproduce the full old Standalone Sample: dynamic source registration and sample slot semantics, actual host transport timing and free offsets, phase vocoder pitch modes, the original eight-subvoice unison ceiling and smoothing behavior, legacy partial extraction, and state transfer across graph rebuilds remain. The new key tracking control permits continuous values, while the old classic mode used an on/off switch; the adjustable release is also an authored v2 behavior. The ten instrument comparisons are native Rust references and do not claim full C++/Lua project parity. A later host-facing Standalone Sample preset format must define those contracts. Sample storage is owned by the prepared graph; decoding and analysis stay outside the audio callback.
